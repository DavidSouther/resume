## Questions

1. As built, REVIEW.md states conclusions inside "Observed" lists, so the packet leans toward answers for questions 2, 3 and 4. Examples: line 61 "Docker's cgroup limits ... are visible to the kernel as the scheduling constraint for all rows" (a causal claim, no cgroup file is captured in `results/final/`); line 35 "The `ucontext` row is close to the `baseline-sigprocmask` row" (pairs the rows so that the syscall cost reads as the cause); line 72 "One `green` handoff is task, scheduler, task (two raw switches plus run queue work)" (an explanation of the 41.1 versus 14.8 gap); line 89 "matches" twice (a verdict on slide 25); line 90 "a blocking call in one task would block the others" (a claim the packet says was not exercised). The request said "Do not answer the following questions." Do you want these sentences reduced to bare counts and file pointers?
2. As built, the ratios `thread / regswitch` about 58, `thread / ucontext` 2.8, `thread / green` 21, `ucontext / regswitch` 21 and the 850, 832 and 635 ns gaps (REVIEW.md lines 70 to 71) are computed in the packet, along with a 428 ns "thread minus baseline-socket" figure (line 35, disclaimed as "not a finding"). The request asked for documentation to review, not derived comparisons for question 3. Is pre-computing these the intended level, or should the author compute them?
3. As built, the `thread` and `process` rows measure a socket pair round trip with a blocked reader and wakeup (`src/bench/mod.rs`), and every number is labelled "ns per switch". `strace` shows 20001 `recvfrom` and 20000 `sendto` for 20000 handoffs. The request asked about "task switching cost". Is a handoff that includes two socket syscalls what you meant by a kernel thread switch, given `baseline-socket` alone is 437 ns of the 865 ns?
4. As built, the `ucontext_t` sizes in REVIEW.md line 40 (4560 bytes aarch64, 968 x86_64, 128 byte mask) come from the `libc` crate struct via `cargo test --release sizes -- --nocapture` (`tests/units.rs:135`). That test is not part of `tests/run.sh`, and its output is not saved under `results/final/`. The request asked for results from running in production containers. Is a number from a crate type definition, with no saved run, acceptable evidence for "what state is saved"?
5. As built, the C originals' `malloc(STACK_SIZE)` stacks (`uctxmake.c`, `umthreaddemo.c`) and `char func1_stack[16384]` stack arrays (`uctxswap.c`) are all replaced by `mmap` stacks with a `PROT_NONE` guard page (`src/stack.rs`; `src/bin/uctxmake.rs:16`, `uctxswap.rs:57,64,70`, `umthreaddemo.rs:22`). `getcontext`/`setcontext` idioms are rerouted through a `global_asm` `ctxswitch_twice` trampoline (`src/uctx.rs`), `sleep`/`usleep` become `std::thread::sleep`, and `uctxrestore` and `uctxswitch` run their body inside `run_twice`. The request said "Port ... to Rust" for teaching examples. Is a guarded-stack, trampolined port, where the stack memory and the `getcontext` call site differ from the course code, what you intended, or do you want a literal port with `malloc`-equivalent stacks?
6. As built, the aarch64 register dump prints `PC, SP, X0` to `X28, FP, LR` (`results/final/programs/uctxmake.txt`), a different list and order from the C `printctx.c` (RIP, RAX, RSP, RBP, RAX, RBX, RCX, RDX, RSI, RDI), which has no aarch64 branch, and the i386 branch of the C original is dropped. The x86_64 list keeps the duplicated RAX for parity but was never run for timing or saved output. Is an aarch64-only register dump in the saved evidence, with the course's x86_64 list unverified in `results/`, what you intended for "what state is saved"?
7. As built, REVIEW.md attributes Dzania and `rsroutine` for the technique and states no code was copied or run, and `green` is single worker only (no M:N, no work stealing, `join` reduced to `take`). The `regswitch` mechanism, which is not in the request, is also credited to the Dzania technique. The later instruction said to add "a 'green threads' approach from" the article and repository. Is a single-worker reimplementation with a separate `regswitch` row acceptable as "the green threads approach", given the `rsroutine` implementation (AAPCS64 `x19`..`x30`, `d8`..`d15`, macOS only) was not itself executed or measured?
8. As built, "in production" is release binaries (`cargo build --release`, `debug = true`) in `debian:stable-slim` with `--cpus=1 --cpuset-cpus=0 --memory=256m --memory-swap=256m --pids-limit=64`, but the benchmark never approaches a limit (256 MiB, 64 pids), runs one container at a time on a Docker Desktop VM, and has no timing from native Linux or x86_64. The request said "Run them (in production)". Is "release build with explicit but non-binding limits on a laptop VM" the intended meaning?

## Mismatches found

- `REVIEW.md:42`: says `uctxmake` dumps "differ in `PC`, `SP` and `X19`, `X20`". Diffing the two dumps in `results/final/programs/uctxmake.txt` shows six registers differ: PC, SP, X19, X20, FP, LR.
- `REVIEW.md:5` and `:75`: "A second run on a loaded machine gave 1173 ns". `results/20261015T002638Z/bench.csv` has `thread,0` = 1173.2, but no load measurement is recorded anywhere; other unlisted runs give 851, 857, 863 (`results/20261015T000445Z`, `...000842Z`, `...004632Z`), so "loaded" is an inference. The run lives outside `results/final/`, which README.md:23 says is the cited raw output. The "about 35 percent" (1173.2 / 864.7 = 1.357) and order claim (`regswitch` 20.3 < `green` 56.8 < `ucontext` 422.5 < `thread` 1173.2 < `process` 1272.3) do hold in that file.
- `REVIEW.md:40`: lists aarch64 registers as "`X0` to `X28`, `FP`, `LR`, `SP`, `PC`"; the program prints `PC`, `SP` first, then `X0`..`X28`, `FP`, `LR` (`results/final/programs/uctxmake.txt`). The order is different from what is documented.
- `REVIEW.md:40`: `ucontext_t` sizes 4560 / 968 / 128 cannot be recomputed from `results/final/`; the only source is `tests/units.rs:135` (not run by `tests/run.sh`). Also described as a "libc definition", not glibc's, so they may differ from the real glibc layout.
- `REVIEW.md:61`: "Docker's cgroup limits ... are visible to the kernel as the scheduling constraint" has no supporting file in `results/final/proc/` (no cgroup or cpuset content captured) and is a causal statement.
- `REVIEW.md:90` and `:78`: claims about "blocking call blocks all threads" and "a 32 KiB green stack versus a 2 MiB OS thread stack" are carried over from the article; the 2 MiB figure is not observed in `results/final/` (the strace shows only 15 and 27 `mmap` calls for setup).
- `REVIEW.md:13`: "every handoff blocks one thread and wakes the other" is a mechanism statement. Observed counters (about 1.00 `nvcsw` per handoff) are consistent with it, but "1.00 per handoff" is computed from `RUSAGE_SELF` totals over two threads, and the definition of "handoff" (one send or a round trip) is not stated; with 2 threads both blocking, 1.00 per handoff implies a handoff is a one-way token pass. Not verified in `src/bench/mod.rs` by this reviewer beyond the counts.
- `REVIEW.md:35`: "Voluntary switches per handoff are `nvcsw` divided by 1,200,000" matches `bench.csv` (1200064 / 1200000 = 1.00005) and the 6 repetitions (5 plus 1 warmup). Verified. The column header "all runs" is accurate only because every `thread` and `process` row is 1.00, which holds (rows 1200026 to 1200076).
- `src/bin/umthreaddemo.rs:42` uses `std::thread::sleep(Duration::from_micros(50_000))` where C uses `usleep(50000)`; `src/bin/uctxrestore.rs:13` uses `std::thread::sleep` where C uses `sleep(1)`. Both are different syscalls (`clock_nanosleep`/`nanosleep`) from libc `usleep`/`sleep`; not listed in REVIEW.md or README.md as ported differences.
- `src/bin/uctxswap.rs:50`, `:57`: the C original prints `%p` of `main` and `func1`; the Rust `{:p}` of `main as fn() -> _` is a monomorphized Rust symbol, not the C `main`. Address lines are not compared by `tests/run.sh`, so the drift is silent.
- `tests/run.sh:136` to `:139`: the attribution check only greps for "dzania" in README.md or REVIEW.md. It does not check H. Chen or Google. Both are present in the docs (README.md:35, :44; REVIEW.md:105), so this is a test-coverage gap, not a doc mismatch.

Attribution to H. Chen, Dzania, `rsroutine` and Google is present and makes no claim that code was copied or `rsroutine` was run (README.md:37 to 43; `src/green.rs:1-11`; `src/stack.rs:1-5`).
